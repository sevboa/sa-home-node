# Фиксапы хоста (`sa_home_node.fixups`)

Фиксап — идемпотентная донастройка машины под назначения и тип ноды: sudoers, polkit, юниты, linger, права,
пакеты, задачи планировщика. Фиксапы применяет человек командой `sa-home-node fix` ([cli](cli.md)); нода их не
запускает.

## Инвариант

`fix` — короткоживущий процесс, не демон. Он читает конфиг локально, по действующим назначениям выбирает
фиксапы и для каждой отрицательной проверки зовёт настоящий интерактивный `sudo` (наследует TTY; пароль нигде не
хранится и не передаётся по сети). Процесс ноды (`run_node`) фиксапы не собирает, не проверяет и не применяет и
`sudo` не вызывает: права хранит человек, нода их только использует. Службам, которым нужен root, фиксапы
ставят узкие sudoers-снипеты (`NOPASSWD` на конкретный путь и аргументы; пути резолвятся заранее — защита от
подмены `PATH`). Подсказка «есть неприменённые фиксапы» появляется только в `fix` и мастере настройки.

## Модули

| Модуль | Что внутри |
|---|---|
| `core.py` | `Fixup`, `FixupContext`, `FixupError`, `FixupReport`, `run_fixups` |
| `needs.py` | предикаты `needed`: `assigned`, `power_controllable`, `wakeable`, `all_of` |
| `registry.py` | `CORE_FIXUPS`, `collect`, `select` |
| `runner.py` | `fix_command` — общий путь для CLI и мастера |
| `privileged.py` | привилегированные примитивы поверх `host.current()` |
| `unit.py` | чистые функции над текстом юнита |
| `node.py`, `autoupdate.py`, `power.py` | фиксапы ядра |

## API

### `Fixup`

`Fixup(id, title, check, apply, needed=always, platforms=("linux",))`:

- `check() -> bool` и `apply() -> None` — без аргументов, замыкания над контекстом;
- `needed(ctx) -> bool` — вычисляется один раз при сборке;
- `platforms` — имена из `host.current().name` (`linux`, `windows`); фиксап другой платформы не попадает ни в
  список, ни в `--list`.

`id` и `title` видны пользователю: `--only` ссылается на id, итоговая строка печатает id упавших. Менять их
у существующего фиксапа нельзя.

### `FixupContext`

Неизменяемый контекст, который получают фабрики:

- `config` — `NodeConfig`;
- `assignments` — действующие назначения (конфиг вместе с `node-state.json`, то есть то, что реально запущено),
  разобранные `parse_valid`;
- `traits` — `NodeTraits` по `[node].kind` с учётом `[node].power_controllable`;
- `host` — `Host` ([host](host.md));
- `assigned(*services) -> bool`, `section(name, model)` (то же, что `config.section`).

`FixupContext.build(config, host)` собирает контекст.

### Ошибки и отчёт

- `FixupError` — ожидаемый сбой; текст на русском попадает в вывод как есть.
- `FixupReport(applied, already, pending, failed)` — списки id.

### `run_fixups(fixups, *, dry_run=False, out=print) -> FixupReport`

Для каждого фиксапа: `check()`; если ложно — `apply()`; затем повторный `check()`. Строки вывода:

- `  ✅ <title> — уже применено`;
- `  ⏳ <title> — применяю (может спросить пароль sudo)...`;
- `  ✅ <title> — применено`;
- `  ❌ <title>: <ошибка>`;
- `  ⚠️ <title>: команда прошла, но проверка всё ещё отрицательна`;
- `  ⚠️ <title>: проверка не удалась (<ошибка>) — пробую применить`.

Правила:

- `FixupError` или `OSError` из `check()` — проверка отрицательна: пробуем `apply()`. Так `sudo cat` без TTY не
  останавливает остальные фиксапы;
- `FixupError` или `OSError` из `apply()` — сбой этого фиксапа; остальные идут дальше, id попадает в `failed`;
- команда прошла, но повторная проверка отрицательна — тоже `failed`.

### `needs`

Предикаты для `needed`: `assigned("svc", ...)` — назначена любая из служб, `power_controllable` и `wakeable` —
по типу ноды, `all_of(...)` — все сразу. Предикаты по службам плагинов (`needs.assigned("svc")`) пишет сам
плагин; ядро имён служб плагинов не знает.

### Привилегированные примитивы (`privileged.py`)

Единственное место, где ядро строит `sudo …` (через `host.elevate_argv`); `subprocess` — только здесь и в
`runner`. Платформа без повышения прав превращается в `FixupError`
(«повышение прав на этой платформе не поддержано — запустите от администратора»).

- `find_executable(name, exclude_dir=None)` — `PATH` плюс `/usr/local/sbin`, `/usr/sbin`, `/sbin`;
- `run_user(argv)`, `run_sudo(argv)` — запуск с проверкой кода возврата;
- `path_exists`, `read_text`, `read_text_if_exists`, `file_matches` — чтение, при `PermissionError` через `sudo`;
- `temp_file`, `install_from`, `install_root_file`, `install_executable` — установка файлов от root
  (`sudo install -m <режим> -o root -g root`; `make_parents` добавляет `-D`);
- `install_sudoers_snippet(name, content)` — проверка `visudo -cf` до установки, режим 0440, каталог `SUDOERS_DIR`;
- `install_package(package, no_manager_message)` — через `Host.package_install_argv`;
- `daemon_reload`, `enable_now`, `unit_is_active`, `replace_unit` — системные юниты.

`unit.py` — чистые функции над текстом: `rewrite_unit_path_line` и `unit_path_first_dir` (строка
`Environment=PATH=`: нужный каталог первым, дубли убираются, остальное не меняется), `exec_command` и
`with_exec_command` (строка запуска юнита форматов `systemd-user` и `winsw`).

## Сборка и порядок

`collect(ctx, plugins)` строит список в таком порядке:

1. фабрики ядра (`CORE_FIXUPS`) в порядке определения:
   - `node_fixups` — `node-linger`, `node-unit-command`, `node-autoupdate-task` (только Windows);
   - `autoupdate_fixups` — автообновление (Windows);
   - `monitor_fixups` — фиксапы монитора (см. ниже);
   - `power_fixups` — `power-control-polkit`;
   - `wol_fixups` — `wol-enable` (Wake-on-LAN на проводном интерфейсе, Linux; `needed` — `needs.wakeable`);
2. фабрики плагинов в порядке `[node].plugins` (`Plugin.fixups`, см. [plugins](plugins.md)); внутри плагина —
   порядок, в котором фабрика вернула фиксапы;
3. фильтр: платформа хоста входит в `platforms` и `needed(ctx)` истинен.

Повтор id — `PluginError` («повтор id фиксапа: x (core, p)»). Исключение фабрики (ядра или плагина) тоже
`PluginError` с именем владельца; при любой такой ошибке не применяется ничего, `fix` завершается кодом 2.
`select(fixups, only)` оставляет перечисленные id в исходном порядке; неизвестный id — `PluginError` со списком
доступных.

Порядок фиксапов важен: зависимые идут после своих предпосылок (пакет, затем sudoers, затем юнит), поэтому
плагин сохраняет его в одной фабрике.

## Фиксапы ядра

- `node-linger` (Linux; нужен юнит ноды `systemd-user`) — `check`: существует
  `/var/lib/systemd/linger/<пользователь>`; `apply`: `sudo loginctl enable-linger`. Без linger нода не
  переживёт выход пользователя из сессии.
- `node-unit-command` (Linux и Windows) — приводит строку запуска юнита ноды к `sa-home-node run --config <путь>`.
  `check`: юнита нет (нода запущена иначе) либо в команде второй аргумент `run` и исполняемый `sa-home-node`.
  `apply` берёт `sa-home-node` рядом со старым исполняемым, иначе из `PATH`; нет — `FixupError`. Путь конфига
  берётся из старой команды как есть; неузнаваемая форма — `FixupError`, файл не тронут. Меняется только строка
  запуска (`ExecStart=` или `<executable>`/`<arguments>` WinSW); `ExecStartPre`, `Environment`, таймауты, BOM и
  переводы строк сохраняются байт в байт. Запись идёт от пользователя; на Windows `PermissionError` — «нужны права
  администратора». На Linux после записи вызывается `systemctl --user daemon-reload`. Ноду фиксап не
  перезапускает — это делает человек.
- `node-autoupdate-task` (Windows) — скрипт автообновления рядом с `config.toml` и задача планировщика
  `sa-home-node-autoupdate` (ежедневно, от SYSTEM), которые ставят пакет `sa-home-node`. `check`: скрипт равен
  отрисованному шаблону и задача зарегистрирована.
- `monitor_fixups` (Linux; `needed` — назначен `monitor` и датчики дисков включены, или назначен `monitor` для
  `journalctl-group`) — фиксапы плагина `monitor` (`fixups/monitor.py`), подробности — [monitor](monitor.md):
  - `install-smartmontools` — пакет `smartmontools` (`smartctl` в PATH);
  - `smartctl-sudoers` — sudoers-снипет `50-sa-home-node-smartctl` + обёртка `~/.local/bin/smartctl`
    (`exec sudo -n <реальный smartctl>`);
  - `node-unit-smartctl-path` — в юните ноды первым в `PATH` стоит `~/.local/bin` (нет юнита — истинно);
    применение переписывает строку и перезапускает юнит;
  - `journalctl-group` — пользователь в группе `systemd-journal`.
- `power-control-polkit` (Linux; `needed` — `power_controllable`) — polkit-правило
  `/etc/polkit-1/rules.d/50-sa-home-node-power.rules`, разрешающее пользователю ноды выключать, перезагружать и
  усыплять машину без `sudo`. `check`: файл существует. `apply`: пакет `polkitd`, если каталога `rules.d` нет;
  `sudo install -d -m 0755`; файл 0644 root.
- `wol_fixups` (Linux; `needed` — `needs.wakeable`) — единственный фиксап `wol-enable`: пакет `ethtool`,
  включение WOL (magic packet) на проводном интерфейсе по умолчанию; юнит
  `/etc/systemd/system/sa-home-wol.service` (oneshot `ethtool -s <iface> wol g`), `daemon-reload`,
  `enable --now`. Подробности — [wake](wake.md).

Плагин `metrics` (встроен) поставляет семь фиксапов при `[metrics].hub = true`:
`install-victoria-metrics`, `metrics-runtime-dir`, `victoria-metrics-config`,
`grafana-repo`, `install-grafana`, `grafana-config`, `grafana-provisioning`.
Порядок, id и что делает каждый — см. [metrics](metrics.md).

## Идемпотентность

Маркер «применено» — сам `check()`: версии фиксапа и журнала применённых нет. Повторный запуск после успеха
печатает «уже применено» для каждого фиксапа и `apply` не зовёт. Фиксап, у которого `check()` истинен без
изменений на диске (юнита нет), тоже считается применённым.

## Dry-run

`--dry-run` вызывает только `check()`; `apply` не зовётся, записей нет (проверка может читать через
`sudo test -e`/`sudo cat`). Отрицательная проверка печатает `  🔍 <title> — нужно применить` и кладёт id в
`pending`; сбой самой проверки печатается без «— пробую применить». Код выхода `fix --dry-run`: 3, если остались
неприменённые, иначе 0.

## Семантика `check()`

Два вида проверки и оба осмысленны:

- «файл есть» — не перезаписывает файлы, поставленные вручную на рабочих машинах; так устроены
  `power-control-polkit`, sudoers-снипеты приложений и мониторинга, unit-файлы с руками подогнанным содержимым;
- «содержимое равно» — переустанавливает файл, когда меняется текст, который генерирует код (обёртки,
  sudoers-снипеты, юниты, чей текст проверяется целиком).

Сводить всё к одному варианту нельзя: «только есть» оставит устаревший текст после правки генератора, «только
равно» заставит `fix` затирать рабочее. Выбор вида — решение автора фиксапа; текст, который сверяется по
равенству, нельзя менять без причины, иначе `fix` переустановит его на каждой машине.

## Отличия от прототипа

Фиксапы, id, заголовки, строки вывода и argv привилегированных вызовов совпадают с прототипом (`nodectl fix`);
отличия намеренные:

- `needed` считается по действующим назначениям (конфиг вместе с `node-state.json`), а не только по конфигу:
  служба, назначенная командой `assign`, получает свои фиксапы;
- `OSError` из `apply()` — сбой одного фиксапа, а не падение всего запуска;
- `fix` работает на Windows: выполняются фиксапы, у которых `windows` в `platforms`;
- флаги `--dry-run`, `--list`, `--only`;
- новые фиксапы: `node-linger`, `node-unit-command`, `node-autoupdate-task`;
- сбой фабрики плагина — ошибка сборки (код 2), ничего не применяется (прототип собирал жёсткий список).

## Почему так

Находки, на которых держатся примитивы и фиксапы:

- **`find_executable` ищет в `sbin`.** Интерактивный `PATH` по SSH (в отличие от `PATH` юнита) не содержит
  `/usr/sbin`. Проверка на голом `shutil.which` не видела уже установленную утилиту, и фиксап вечно висел в
  состоянии «команда прошла, проверка отрицательна».
- **Минимальная установка без polkit.** Каталога `/etc/polkit-1` нет, и `install` падает с ENOENT. Пакет
  `polkitd` ставится, если `rules.d` нет; затем `install -d`.
- **Приватные каталоги.** Каталог под `umask 077` не читается пользователем: голый `stat` падает с
  `PermissionError`, даже когда файла нет. `path_exists` переспрашивает через `sudo test -e`, иначе `apply`
  решил бы, что файла нет, и затёр бы рабочий.
- **Падение `check()` не останавливает запуск.** Необработанный `FixupError` из проверки (например `sudo cat`
  без TTY и без кэша пароля) раньше обрывал все оставшиеся фиксапы; теперь проверка считается отрицательной.
- **`visudo -cf` до установки.** Снипет с ошибкой синтаксиса, установленный в `/etc/sudoers.d`, ломает `sudo`
  целиком; поэтому сначала проверка временного файла и только потом `install` с режимом 0440.
- **Правка юнита — только заменой нужной строки.** Остальное (`ExecStartPre`, таймауты, `Environment`) на
  рабочей машине настроено руками и не должно меняться; `rewrite_unit_path_line` ставит каталог обёртки первым в
  `Environment=PATH=` и убирает дубли.
- **Обёртка и sudoers.** `sudo` без пароля сам по себе ничего не даёт, если код зовёт голое имя команды:
  нужна обёртка (`exec sudo -n <настоящий путь> "$@"`), стоящая в `PATH` юнита первой. Настоящий путь
  ищется с исключением каталога обёртки (`exclude_dir`), иначе повторный запуск поставил бы sudoers-снипет на сам
  скрипт.
- **Фиксап, ставящий право после смены группы.** Членство в группе не доходит до уже запущенного пользовательского
  менеджера systemd (при linger он держит старые группы): `apply` должен назвать точную команду
  перезапуска, а проверка по `id -nG` одна этого не покажет.
- **Узкие права.** Sudoers-правило даёт не программу целиком, а конкретные подкоманды: утилита, способная
  исполнять произвольные хуки, под `NOPASSWD` — это root.
- **Побайтовая стабильность.** Генерируемые sudoers, юниты и скрипты сверяются побайтно (`check()` ряда фиксапов
  сравнивает содержимое с ожидаемым); менять их текст без причины нельзя.

## Как написать фиксап плагина

Плагин кладёт в `Plugin.fixups` фабрику `(FixupContext) -> Sequence[Fixup]`; пример и правила — в
[plugins](plugins.md). Привилегированные действия идут только через примитивы `privileged.py`.
