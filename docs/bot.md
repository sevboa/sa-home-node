# Оболочка Telegram-бота (`sa_home_node.bot`)

Оболочка — встроенный плагин `bot` (`sa_home_node.bot.plugin.PLUGIN`): процессная служба `telegram-bot`
(синглтон, с экземплярами и сателлитом `.guests`). Она держит long polling, рассылает в чаты события
монитора и роя, показывает панель роя и управляет гостями. Предметные команды и экраны приносят другие
плагины через `BotSpec` (см. [plugins](plugins.md)); оболочка о них ничего не знает.

Связь с остальной нодой идёт через три `ServiceLink` (сокеты служб `node`, `monitor`, `apps`): состояние,
команды, подписка на события, автопереподключение (`RECONNECT_DELAY_S`). Описание протокола —
[protocol](protocol.md), роя — [swarm](swarm.md), монитора — [monitor](monitor.md).

## Два барьера и модель прав

Каждый апдейт проходит два барьера (`middlewares.py`).

1. `SilenceGate` (внешний, на весь апдейт). Если чат есть в `SubscriptionBook` — апдейт идёт дальше. Иначе
   текст сообщения проверяется как инвайт-код (`Gatekeeper.try_admit`); при успехе в данные кладётся
   `admission`, при неудаче апдейт молча отбрасывается: чужой чат не получает ни ответа, ни отказа.
2. Авторизация. `AuthorizationMiddleware` для сообщений и `CallbackAuthorizationMiddleware` для кнопок
   кладут в данные `subscription` и проверяют право. Универсальная команда (`universal=True`) доступна
   всем подписанным; управляющая требует права; при отказе сообщение «команда недоступна», на кнопке —
   всплывающее «недоступно».

Модель прав — множество строк в `Subscription.allowed_commands`:

- `команда` — право на команду реестра (или на её `right`, если оно задано: `/swarm` требует `nodes`,
  `/invite` и `/guests` — `invite`);
- `действие@служба` — право на конкретное действие службы; `*@служба` — на все действия службы.
  Голое имя действия тоже засчитывается (для старых записей);
- `*` — владелец: разрешено всё, такие подписки получают служебные рассылки для админов.

События подписки задаются отдельно: `event_types` (с `*`) и `except_event_types`. Битая подписка
(`broken`) не получает ничего. Право на кнопку действия можно дать и защитой плагина:
`BotSpec.callback_guards` — функции `(подписка, служба, действие) -> bool`, любая вернувшая `True` пропускает.

Список выдаваемых гостям прав задают плагины через `BotSpec.guest_rights` (`RightGroup` из `GuestRight`);
`RightsCatalog` собирает их, даёт подписи и отдаёт множество `grantable` (группы без `fine`, без `*`).
Устаревшие права отсеивает `RETIRED_RIGHTS` в `book.py`.

## Реестр команд и callback_data

`Registry` собирается из встроенных команд и `BotSpec.commands` (`Command`: имя, описание, `universal`,
`menu`, `right`, `callback_codes`). Плагинная команда с тем же именем заменяет встроенную.

Форматы `callback_data` — контракт с уже отправленными сообщениями: кнопки в чатах живут долго, поэтому
менять префиксы и коды нельзя, только добавлять новые.

| Формат | Пример | Разбор |
|---|---|---|
| `st:<код>[:аргумент...]` | `st:sw_node:alpha` | `panel_callback`, `Registry.command_for_callback`: код → команда → право |
| `act:<служба>:<действие>[:значение[:нода]]` | `act:node:check_update` | `action_callback`, `parse_action_callback`: право `действие@служба` |
| `st:wake[:нода]` | `st:wake:alpha` | `wake_callback`, `parse_wake_callback` |

Коды панели роя (`sw_*`, `nodes`, `nodecard`, `svc`, `downtime_page`) привязаны к командам таблицей
`_CODE_MAP`; коды гостевых экранов (`g_*`) перечислены в `callback_codes` команды `/guests`. Кнопка с
неизвестным кодом не блокируется барьером и уходит дальше по роутерам. Лимит Telegram на `callback_data` —
64 байта: аргументы должны быть короткими.

Встроенные команды: `/ping` (универсальная), `/swarm` и `/nodes`, `/status`, `/status_full`, `/stats`,
`/scan_now`, `/downtime`, `/wake`, `/invite`, `/guests`.

## Гости и приглашения

Гостевая подписка появляется, когда незнакомый чат присылает действующий код (`/start <код>` или просто
текст кода).

- Формат кода (`gate.py`): 8 символов алфавита Crockford (`0-9A-Z` без `I L O U`), для показа
  группируются по 4 через дефис. `normalize` убирает пробелы, дефисы, точки и подчёркивания, переводит в
  верхний регистр, заменяет похожие `I`, `L` на `1` и `O` на `0`; сырой ввод длиннее 16 символов — не код.
- Жизнь кода: выпуск (`/invite`, срок `invites.ttl_s`) → погашение одним чатом → запись в таблицу
  `invites`. Погашенный, отозванный и просроченный коды больше не работают; открытые видны и отзываются в
  `/guests`.
- Лимитер `AttemptLimiter`: не более `invites.max_attempts_per_hour` попыток на чат в скользящем окне часа.
  Сверх лимита чату не отвечают; в момент исчерпания админам уходит одно предупреждение о подборе кода.
  Успешное погашение сбрасывает счётчик.
- Права нового гостя берутся из `invites.grant_commands` и `invites.grant_events`. После допуска вызывается
  `BotSpec.on_admitted` (цепочкой по плагинам) — плагин может поприветствовать гостя.
- Приглашения работают, только если включены и доступно хранилище гостей (`Gatekeeper.enabled`).
- Гостевой пакет: гостей хранит и переписывает целиком только бот — `GuestStore` пишет атомарно файл
  `[[guest_subscriptions]]` (`guestfile.py`, с заголовком «файл ведёт бот»). Это сателлит `.guests`
  пакета экземпляра: он реплицируется по рою вместе с основным пакетом, поэтому гости переживают переезд
  бота на другую ноду. Ручные правки в нём не сохраняются; владельческие подписки правятся в основном пакете.
- Экраны `/guests` (`guestsview.py`, `handlers_invites.py`): список гостей и кодов, карточка гостя, включение
  и выключение групп прав и отдельных прав, отзыв гостя с подтверждением, учёт использования
  (`BotContext.guest_usage`, по умолчанию «учёт не ведётся»).

## Меню

`menu.py` строит меню команд Telegram для каждого чата отдельно (`BotCommandScopeChat`): действия
навыков службы `apps` без параметров (если право есть), управляющие команды с `menu=True`, на которые у
подписки есть право, и универсальные. Глобальные команды бота удаляются, чат без подписки меню не получает.
Меню обновляется при старте и при каждом (пере)подключении ссылки на `apps`; `refresh_chat_menu`
обновляет один чат (после допуска или смены прав).

## Панель роя и карточки

`/swarm` (`swarmpanel.py`, `swarmview.py`, `nodeview.py`) собирает отчёты нод через службу `node`:
сводка (версии, число уникальных служб и навыков), постраничные списки нод (по 5) и навыков (по 6),
карточка ноды, карточка службы, карточка навыка; кнопка «разбудить» для спящих нод (`handlers_wake.py`, с
`BotSpec.wake_guard` — плагины могут отклонить пробуждение), кнопка проверки обновлений (`check_update`).
Все экраны правят одно сообщение (`edit_text`), навигация идёт по `st:sw_*`. Кнопки действий над нодой и
службой — `act:...` и проверяются по правам `действие@служба`. Остальные команды (`/status`,
`/status_full`, `/stats`, `/scan_now`, `/downtime`) читают состояние службы `monitor` и рисуют его через
`render_status.py`, `render_alerts.py`.

## События монитора и роя в чаты

- Монитор → `AlertDispatcher` (`alerts.py`). Перегрев и его снятие идут с записью в `EventStore`: тревога
  и отбой связываются, отбой отвечает (reply) на сообщение тревоги; доставка через outbox с ключом
  дедупликации по компоненту. Деградация диска (SMART) и события хоста рассылаются без outbox. Получатели —
  `SubscriptionBook.accepting(тип события)`. Невалидное событие пишется в лог и пропускается.
- Рой → `build_node_event_handler` (`nodeevents.py`): вход, падение, возврат и уход ноды, смена
  активной ноды синглтона, итог обновления и применённый рестарт — текстом в системный поток
  (`broadcast_system`, подписка на системные события) с записью в `EventStore`. Событие «простой не даёт
  выключить машину» идёт только админам, с кнопкой закрытия SSH-сессий и защитой от повторов в минуту.
- События, которых оболочка не знает, отдаются плагинам: `BotSpec.event_routes` (`EventRoute(names, handle)`).
  Маршрут выбирается по имени события.
- Рассылки: `broadcast`, `notify_admins` (подписки с `*`), `broadcast_system`, `broadcast_all`.
- Жизненный цикл самой оболочки (`lifecycle.py`): при старте — «снова на посту» (штатно) или «после
  сбоя» с последним отключением машины из монитора; при останове — «уходит в офлайн»; признак штатности
  хранится в `AppState`. После долгой потери связи с Telegram `LinkWatchMiddleware` сообщает, сколько
  был офлайн.

## Доставка

- `send_with_retry` (`send.py`): до 3 попыток с паузами 0, 2, 5 с; 429 ждёт `retry_after + 1`.
  Перманентные ошибки (неверный запрос, запрет, чат не найден) без повторов. Ошибка разбора разметки →
  `Notifier` повторяет отправку без `parse_mode`.
- `chunk_text`: сообщение длиннее 4096 символов режется по переводу строки; кнопки и reply — только у
  первого куска.
- Outbox (`store_outbox.py`, `outboxflush.py`): если отправка упёрлась во временный сбой (связи нет),
  остаток сообщения кладётся в очередь в БД с видом и ключом дедупликации. Срок жизни по виду: тревога 6 ч,
  задача и доставка 24 ч, интерактив 15 мин; просроченное удаляется. `OutboxFlusher` разбирает очередь по
  таймеру и по сигналу `kick` (восстановление маршрута); сообщение старше минуты получает пометку
  «с задержкой». Перманентная ошибка удаляет запись; сетевая прерывает проход и увеличивает счётчик попыток;
  не более трёх ожиданий 429 за проход.
- Вложения: `AttachMixin` (`attach.py`) — документы, фото, группы до 10, голос.
- Запуск устойчив к сети: `get_me` при старте идёт через `call_with_network_retry`.

## Маршрут до Telegram

`telegram.proxy_mode`: `fixed` — один прокси из `telegram.proxy` (или прямой), `auto` — менеджер маршрута
(`egress.py`, `egressmanager.py`).

- На старте порядок кандидатов: сохранённый в `egress_state_path` маршрут, `telegram.proxy` (или прямой),
  прямой, затем `extra_proxies` (SOCKS); берётся первый, с которого отвечает Telegram.
- `TroubleDetector` — middleware запросов: 3 сетевых сбоя подряд или 60 с без успеха — «беда», что
  запускает внеочередную оценку; первый успех после беды — сигнал восстановления (сбрасывает очередь outbox).
- Раз в `TICK_S` (5 мин) `choose_route` выбирает маршрут: прямой жив и (`prefer_direct` или он уже
  текущий) — прямой; возврат на прямой — после `DIRECT_RETURN_STREAK` успешных проб подряд; уход с прокси —
  когда текущий негоден или лучший как минимум вдвое быстрее и выигрывает больше 300 мс. Проваленный
  кандидат банится на 15 мин.
- Кандидатов поставляют плагины: `BotSpec.egress_candidates(ctx)` возвращает асинхронный источник списка
  словарей; плагин с собственными прокси сам решает, что считать кандидатом. `telegram.extra_proxies` — статика.
- Смена маршрута применяется к сессии без перезапуска (`apply_route`), сохраняется в файл состояния и
  сообщается админам через `SwitchNotices` (не чаще раза в 10 минут). Сообщение при недоступном Telegram
  уходит в outbox и доедет после смены.

## Порядок роутеров и почему

`setup.build_dispatcher` включает роутеры строго в таком порядке; первый подошедший хендлер побеждает.

1. `handlers_invites` — коды приглашений и экраны гостей: допуск нового чата не должен перехватываться ничем.
2. Плагинные роутеры с `order < 100` («раньше всех»): перехват текста до оболочки.
3. `handlers_wake`, `swarmpanel` — узкие команды и кнопки роя (`st:wake`, `st:sw_*`): они обязаны стоять раньше
   `handlers_status`, который ловит весь префикс `st:`.
4. Плагинные роутеры с `100 <= order < 900` — основная зона плагинов.
5. `handlers_status`, `nodelinks`, `handlers_node` — состояние и действия над нодами.
6. `handlers_basic` — `/start` и `/ping` (при `/start` с кодом — допуск) и ответ на любую неизвестную `/`-команду,
   поэтому он последний среди роутеров оболочки.
7. Плагинные роутеры с `order >= 900` — «после всех»: разбор свободного текста, который не должен
   съедать команды.

Внутри зоны плагинные роутеры сортируются по `order`. Плагинные `middlewares` вешаются после барьеров,
поэтому видят уже авторизованные апдейты.

## BotSpec и пример плагина

`Plugin.bot` — необязательный `BotSpec` (`spec.py`); плагины без него оболочку не затрагивают. Поля:

| Поле | Что даёт |
|---|---|
| `commands` | команды реестра |
| `routers` | `RouterSpec(order, build)`: `build(ctx)` возвращает aiogram `Router` |
| `middlewares` | пары `(имя события aiogram, фабрика)`, например `("message", f)` |
| `guest_rights` | группы прав для гостей |
| `event_routes` | обработчики событий роя, которых нет у оболочки |
| `schema` | SQL-схемы, применяемые к БД бота при открытии |
| `callback_guards` | дополнительные разрешения на кнопки действий |
| `help_lines` | строки для `/help` |
| `subscription_tags` | `config -> {chat_id: теги}` для подписок |
| `egress_candidates` | источник кандидатов для менеджера маршрута |
| `on_admitted` | реакция на допуск гостя |
| `on_start`, `on_stop` | хуки до начала и после конца polling |
| `wake_guard` | вето на пробуждение ноды: возвращает текст отказа или `None` |

`BotContext` (`context.py`) даёт плагину бот, подписки, `notifier`, хранилища, три ссылки на службы,
реестр, каталог прав, гейт и конфиг. Минимальный плагин (`tests/bot/stub_plugin.py`):

```python
def _build_router(ctx: BotContext) -> Router:
    router = Router(name="stub")

    @router.message(CommandFilter("hello"))
    async def hello(message: Message) -> None:
        await message.answer("Привет из заглушки")

    return router


Plugin(
    name="stub",
    bot=BotSpec(
        commands=(Command(name="hello", description="приветствие", universal=False, right="hello@stub"),),
        routers=(RouterSpec(order=500, build=_build_router),),
        guest_rights=(RightGroup("stub", "Заглушка", (GuestRight("hello@stub", "Приветствие"),)),),
        event_routes=(EventRoute(frozenset({"stub_ping"}), relay_ping),),
    ),
)
```

## Конфиг пакета экземпляра

Служба `telegram-bot` — экземплярная: пакет настроек лежит в `instances/telegram-bot.<экземпляр>.toml`
рядом с `config.toml` (см. [services](services.md)). Секция плагина в `config.toml` — `BotServiceConfig`:

| Поле | По умолчанию | Смысл |
|---|---|---|
| `config_path` | `./data/bot.toml` | основной конфиг бота |
| `guests_path` | нет | файл гостей (сателлит); без него приглашения выключены |
| `db_path` | `./data/bot.sqlite` | БД бота |
| `monitor_socket`, `apps_socket` | `./data/monitor.sock`, `./data/apps.sock` | сокеты служб |
| `egress_state_path` | `./data/egress.json` | состояние маршрута |

`load_bot_config` сливает три источника: основной конфиг, пакет экземпляра (перекрывает одноимённые
секции с предупреждением) и гостевой файл. Берутся только известные секции:

- `[telegram]` — `token`, `proxy`, `proxy_mode` (`fixed`/`auto`), `extra_proxies`, `prefer_direct`;
- `[invites]` — `enabled`, `ttl_s` (3600), `grant_commands`, `grant_events`, `max_attempts_per_hour` (5);
- `[wake]` — `mac`, `ip`, `broadcast`, `port`, `wait_timeout_s`;
- `[[subscriptions]]` — `name`, `chat_id`, `event_types` (по умолчанию `["*"]`), `except_event_types`,
  `allowed_commands`;
- `[[guest_subscriptions]]` — то же плюс `invited_by_chat_id`, `invited_at`, `invited_user` (ведёт бот);
- `about_name` — имя в текстах.

Токен и идентификаторы чатов живут только в приватных конфигах, не в репозитории.

## Находки

- Два экземпляра бота с одним токеном не уживаются: второй получает конфликт (409) и уступает, служба
  завершается как вытесненная, чтобы синглтон перешёл соседу. О старте объявляют только после фактического
  начала polling, иначе при сбое старта чаты получили бы ложное «на посту».
- Тревога не должна пропадать из-за временной потери сети, поэтому тревоги перегрева идут через outbox,
  а менее критичные рассылки — напрямую.
- Ошибка разметки HTML в тексте плагина не теряет сообщение: оно повторяется простым текстом.
- Слово «running» у службы не доказывает, что бот отвечает: проверять нужно запись о запуске в логе.
- 2026-11-26: плагин `bot` грузится на каждой ноде, а `aiogram` занимает ~140 МБ RSS. Служба
  `telegram-bot` импортирует `bot.run` только при запуске (`run_telegram_bot` в `bot/plugin.py`): нода без бота
  на Python 3.11 весила 191 МБ вместо ~45. Страж — `test_load_plugins_does_not_import_aiogram`.
