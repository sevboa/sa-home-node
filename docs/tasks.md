# Служба tasks (`sa_home_node.tasks`)

Отложенные задачи роя: заказчик (плагин или любая нода) ставит задачу с моментом срабатывания, служба в срок исполняет
протокольную команду и сообщает итог событием. Плагин `tasks` (`tasks/plugin.py`) подключает процессную службу
`tasks` (сокет `[tasks].socket`); обычно она живёт на той же ноде, что и заказчик.

## Модель задачи (`tasks/store.py`)

Задача = `due_at` + команда (`dst_node`, `dst_service`, `action`, `args`) + `timeout_s` + непрозрачные `meta`.
Служба `meta` не читает: хранит и целиком возвращает в событиях тому, кто задачу создал. Доставка пользователю и
учёт у заказчика остаются на заказчике.

БД службы — SQLite (`[tasks].db_path`), схема `SCHEMA`:

- `tasks`: `id`, `dst_node`, `dst_service`, `action`, `args_json`, `timeout_s`, `meta_json`, `due_at`, `created_at`,
  `fired_at` (NULL — ещё не списана), `prewake_done` (прогрев уже запускался);
- `event_waiters`: `task_id`, `node`, `event_type`, `created_at` — задачи, ждущие событие роя;
- `app_state`: ключ-значение.

Время хранится в UTC в ISO 8601. Конфиг (`TasksConfig`): `socket`, `db_path`, `default_timeout_s` (240, бюджет задачи
без своего `timeout_s`), `warmup_timeout_s` (360, потолок прогрева).

## Протокол (`tasks/protocol.py`, `tasks/service.py`)

Константы протокола не импортируют ничего из проекта, чтобы заказчик мог их брать, не подтягивая службу.

Действия службы:

- `create` — поставить задачу. Обязательны непустые строки `due_at` (ISO 8601; без пояса считается местным временем),
  `dst_node`, `dst_service`, `action`. Необязательны `args` и `meta` (объекты), `timeout_s` (число), `await_event`
  (`{node, event_type}`: ждать событие роя вместо времени, `due_at` остаётся страховкой). Ответ: `{"task_id": id}`.
  Ошибки формата — `ERR_BAD_REQUEST`.
- `fire_now` (`task_id`) — разбудить задачу раньше `due_at`. Идемпотентно: `{"fired": false, "reason": ...}` для
  неизвестной или уже сработавшей задачи; защита от двойного срабатывания — `fired_at IS NULL`.
- `match_event` (`node`, `event_type`) — сверить событие роя с ожидающими: берёт самую раннюю задачу-ждуна
  (waiter снимается), будит её как `fire_now`; ответ `{"matched": bool, "task_id"?}`. Сверка живёт в службе, потому что
  задача, сработавшая по событию, сама ставит следующее ожидание изнутри службы.
- `timer` — действие-«будильник», см. ниже.

События службы (рассылаются через `ctx.broadcast`):

- `task_prewake {task_id, meta, status}` — прогресс прогрева: `waking` (идёт подъём цели; один раз на задачу) и `ready`;
- `task_result {task_id, meta, ok, result?, error?}` — итог на сроке: `ok=True` с `result` или `ok=False` с `error`.

## Виды задач (`tasks/kinds.py`)

`TaskKind` описывает исполнителя действия, которое служба не форвардит как обычную команду:

| Поле | Смысл |
|---|---|
| `action` | имя действия в задаче |
| `execute(TaskCall)` | исполнение, возвращает словарь результата |
| `wait_ready` | перед исполнением дождаться готовности цели (иначе провал с ошибкой) |
| `prewake` | будить цель заранее (по умолчанию да) |
| `retry(exc)` | можно ли повторить после этой ошибки (по умолчанию никогда) |

`TaskCall` передаёт исполнителю `task_id`, адрес цели `dst`, `args`, `meta`, `timeout_s`, общий срок `deadline`,
`link` и `emit` (отправка событий роя). Плагины добавляют виды через `Plugin.task_kinds`; задача с действием, которого
нет среди видов, форвардится цели обычной командой с `timeout_s`, и результат ответа уходит в `task_result`.

Встроенный вид `TIMER` (`timer`): исполнять нечего, на сроке сразу `task_result {ok: true, result: {}}` с `meta`
заказчика; цель не будится (`prewake=False`), `dst_node`/`dst_service` формальны. Нужен для срока, который должен
пережить рестарт заказчика (например, истечение формы подтверждения).

## Прогрев и срабатывание (`tasks/loops.py`)

Константы (`tasks/protocol.py`):

| Константа | Значение | Смысл |
|---|---|---|
| `PREWAKE_LEAD_S` | 600 с | за сколько до срока начинается прогрев |
| `POLL_INTERVAL_S` | 30 с | период опроса очереди обоими циклами |
| `FIRE_GRACE_S` | 300 с | сколько после срока ещё пытаемся исполнить |
| `FIRE_RETRY_INTERVAL_S` | 30 с | пауза между повторами на сроке |

`TaskRunner` держит два цикла.

Прогрев (`prewake_loop` -> `prewake_due`): задачи с `due_at` не позже «сейчас + `PREWAKE_LEAD_S`» и `prewake_done=0`
помечаются сразу (чтобы следующий тик не запустил второй прогрев), затем для видов с `prewake` стартует фоновая попытка
`ensure_service_ready` (см. [wake](wake.md)). Если цель уже отвечает и не спит, прогрев не нужен. Иначе один раз
эмитится `task_prewake waking`; при `READY` — `task_prewake ready`. Неудача прогрева ничего не эмитит: на сроке будет
серия повторов.

Срабатывание (`fire_loop` -> `fire_due`): задачи с `due_at` в прошлом сразу списываются (`fired_at`, снятие waiter) и
исполняются в фоне; медленное исполнение не может попасть под повторный тик. Порядок `_fire_one`:

1. Если идёт прогрев этой же задачи, дождаться его (не дольше `FIRE_GRACE_S`), а не читать присутствие посреди него.
2. Неизвестное действие: команда цели с `timeout_s`; ошибка связи даёт `task_result ok=False`.
3. Известный вид: общий срок `deadline = сейчас + FIRE_GRACE_S`. Если `wait_ready`, цель будится и прогревается повторами
   каждые `FIRE_RETRY_INTERVAL_S` до `deadline` (ожидание подъёма и прогрев не выходят за остаток бюджета); не
   поднялась — `task_result ok=False` с ошибкой «цель недоступна/не прогрета к моменту срабатывания».
4. `execute` вида; при сбое связи и `retry(exc)` исполнение повторяется до `deadline`, иначе итог — `ok=False`.

Правило опоздания: задача исполняется в окне `[due_at, due_at + FIRE_GRACE_S]`; позже честный отказ полезнее
запоздавшего исполнения. Холодный старт цели не растягивает срабатывание сверх этого окна.

## Недоступность

Сбой «цель недоступна в моменте» не повод сразу сдаваться: вид сам решает через `retry`, какие ошибки повторять
(как правило, временную недоступность); детерминированные ошибки (плохой запрос, внутренний сбой) повтор не лечит и
сразу уходят в `task_result ok=False`.

## Права заказчика

Права заказчика (кто и что может запросить) проверяет плагин, который добавил вид: в момент срабатывания, по `meta`, а
не снимком при создании, чтобы отобранное право не работало у ждущей задачи. Ядро этого не знает и в `meta` не
заглядывает. Событиям, которые вид отправляет изнутри исполнения (через `TaskCall.emit`), заказчик отвечает сам.

## Запуск (`tasks/run.py`, `tasks/link.py`)

`make_handler` строит `OwnedTasksService`: БД, `NodeLinkClient` (связь с локальной нодой по сокету с токеном роя,
одно переподключение при обрыве, таймаут пробрасывается как есть), виды `[TIMER, *виды плагинов]`, `MemoryWakeCache` и
`TaskRunner`. `run_tasks` открывает БД, применяет схему (`apply_schema`), запускает циклы и ждёт; при остановке
гасит задачи, закрывает связь и БД. Служба описывает свои действия через `describe()`; `get_state` отдаёт узел и имя
службы.
